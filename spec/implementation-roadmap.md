- 日期：2026-10-19
- 状态：工作包与门禁设计持续维护；S2-02/B3 已完成接纳与持久任务基础子阶段，未宣称完整部署能力
- 相关文档：[前端](frontend-implementation.md)、[后端](backend-implementation.md)、[共享契约](api-contract.md)

## 1. 推进规则

先证明 Docker 路线与核心契约，再完成部署和运维闭环。前端可在阶段 0 用 fixture 建布局与隔离测试；真实部署功能进入阶段 2 前必须通过阶段 0。没有必要增加其他生产运行实现。

每个工作包交付实现、生产调用点、相应测试、异常恢复与证据；依赖未完成时不得用模拟成功替代。接口改动同步更新契约及两端测试。未知的运行条件必须作为阻断或待核实暴露，不能默认成功。

P0：主机管理、列表、Docker 部署/启停、隔离、世界/MOD、更新备份恢复、有限诊断和任务失败恢复。P1：远端定时备份/保留、健康历史/诊断包、旧部署迁移。P2：模板复制、通知、自愈等。本版将规划阶段 4 内的 P1 项单列验收，避免拖累或混淆 P0 门禁。

## 3. 阶段 0 实验与放行

测试主机从干净 Ubuntu 26.04 LTS 开始，初始无 Docker 包/daemon；通过应用的 root SSH 安装器执行 Docker Engine/Compose 安装并验证 task 断线对账。随后需具备可观察 Docker/网络/磁盘权限，并可从不同外部网络执行玩家连接。记录主机发行版/内核/架构、APT 源签名、Docker/Compose 精确版本、资源、runtime/worker 镜像 digest、SteamCMD 获取方式、DST build、MOD 版本/摘要、脚本 checksum。

实验使用 A/B/C 三实例，每个开启 Master/Caves，各自名称/认证密钥/数据/UGC/端口。至少一个实例有可配置 MOD。不能只运行空容器或同一个世界的三个副本冒充完整隔离。

| 编号 | 实验 | 通过条件/证据 |
| --- | --- | --- |
| N01 | 同机三实例创建启动 | label/manifest/项目/网络/mount/完整端口可对应，三实例同时运行 |
| N02 | 对外同号端口 | 生成配置、Docker publish、真实 UDP listener 一致，Steam 全套端口完整 |
| N03 | Master/Caves | A/B/C 内部分片端口可重复但网络独立，双向迁移只到所属实例 |
| N04 | 公网大厅 | 每实例可发现；记录登记/查询证据，身份与预期实例相符 |
| N05 | 玩家/直连/Steam 查询 | 从外部网络进入并检查游戏数据；每条路径命中目标，不能只凭 N04 |
| N06 | LAN 发现 | 游戏端口在支持范围，局域网客户端可发现；范围耗尽明确阻断 |
| N07 | MOD/UGC | 两分片目标 MOD 一致，无并发写同一 UGC；自动下载行为/权限已记录 |
| N08 | 发布切换 | staging 不改变活动产物，切换仅 A；实际 build/MOD 与目标一致 |
| N09 | 回滚 | 旧 build+MOD+配置+存档恢复点完整，恢复后可进入/迁移 |
| N10 | SSH/桌面断开 | controller/worker 继续，锁未提前释放；重连按 taskId 对账，不重复变更 |
| N11 | worker/daemon/主机异常 | journal 足以判定或显式 interrupted；不会自动重跑破坏性阶段 |
| N12 | 开机启动/手动停止 | daemon/主机重启、重建后行为与产品定义一致 |
| N13 | 权限/秘密 | 非 privileged、不挂 socket、mount 不越界，inspect/log/status 不含秘密 |
| N14 | 资源预算 | 三实例资源、更新/备份峰值空间与耗时有实测；首发环境下限可描述 |

阶段 0 输出 `spec/evidence/stage-0-report.md`（实际实验时创建），至少包括：环境与命令摘要、脱敏配置/端口表、每个 N 的结果/日志位置、失败原因/修复/复测、产物获取约束、最终容器拓扑、UGC 方案、任务监督方式、开机策略、受支持环境与未支持条件。

当前文档没有创建空“已通过报告”。若测试条件缺少公网/LAN 客户端、旧产物或真实 MOD，记录未测并阻断对应放行，不能替换成推测通过。

## 5. 后端并发、更新与恢复验收

| 编号 | 场景/故障注入 | 预期 |
| --- | --- | --- |
| B01 | 两客户端同时创建 | 注册/端口唯一，无默认目录，无互相覆盖 |
| B02 | 同实例同时更新/恢复/启停/保存 | 单个有效 owner/pendingTask，其他写入 INSTANCE_BUSY |
| B03 | A/B 两重型任务 | FIFO 队列，最多一个重型 worker；C 可只读和游戏运行 |
| B04 | lease 超时但进程仍持 flock | 不夺锁、不 unlink；进入对账 |
| B05 | 旧 owner 释放/提交 | token/generation 拒绝，不影响新任务 |
| B06 | 外部进程抢占预留端口 | 启动前/后验证失败，保留身份/端口/现场 |
| B07 | 伪造 host/instance/path/Compose name | 拒绝且远端文件不变 |
| B08 | 重试同 operationId/不同输入 | 同输入关联原结果；不同输入明确拒绝 |
| B09 | 队列等待导致 plan/revision/空间变化 | 执行前重查，PLAN_STALE 或容量阻断 |
| B10 | registry/manifest 写一半断进程 | journal 对账，写入冻结到恢复完成 |
| R01 | 备份 checksum/来源/schema 异常 | 拒绝保护/恢复，不删原世界 |
| R02 | B 备份在 A 恢复 | BACKUP_TARGET_MISMATCH |
| R03 | 下载/解压/备份时磁盘满 | 无假成功，保护点仍在，可清 staging |
| R04 | 更新保存新版本世界后回滚 | 旧程序+MOD+配置+存档一致，非只切二进制 |
| R05 | 旧 build 或 MOD 产物缺失 | 禁自动回滚，预览明确恢复限制 |
| R06 | 每个 publish/restore rename 断点崩溃 | 识别已完成/未完成阶段，不重复破坏性写入 |
| R07 | 更新失败且回滚失败 | 原任务 failed，现场/保护点保存，给恢复入口 |
| R08 | A MOD/DST/世界变更 | B/C 配置/数据/产物摘要与运行证据不变 |
| R09 | 删除中途断线/失败 | retired/任务可发现；未确认清理不放端口 |
| R10 | 备份/任务 GC | 活跃、interrupted、唯一恢复点/引用产物不被清理 |
| R11 | archive 路径穿越、symlink、容量膨胀 | 解压前或受限 staging 拒绝，不写管理根之外 |
| R12 | 秘密样本进入错误/日志/诊断/DB | 持久化前脱敏或排除，无明文秘密 |

R08 比较测试前后 B/C manifest、world/MOD/config/data 相关摘要，区分游戏正常运行会自然变化的存档。要验证“不受影响”，应对比静态配置/产物、维护任务与玩家连续性，并控制存档采样窗口，不能要求运行中的所有文件永远字节不变。

P1 增补：定时备份在桌面关闭后执行、时间/时区/重启去重、任务冲突排队、保留引用；迁移失败恢复旧服务与端口，旧目录完整，新旧世界不并发写；诊断导出容量、分页与秘密过滤。

## 6. 自动门禁与发布

前端：vue-tsc、test:frontend、build。后端：cargo fmt/check/test/clippy（-D warnings）。脚本：bash -n + 隔离场景；数据库：空库/升级/删除/事务/秘密；接口改动：同时跑前后端。所有修改 git diff --check，发布检查产品版本/安装包/脚本/协议一致。

文档阶段只检查 Markdown、链接、契约一致性与覆盖关系，不运行当前并不存在的新工程脚本，也不声称 Docker 已验收。

P0 放行条件：

1. S0 全部证据完成，首发环境、容器/UGC/后台方式冻结。
2. P0 主路径可用；F/B/R 中适用 P0 场景通过，安全/身份/数据隔离问题为阻断。
3. 四组视觉与键盘交互通过；失败恢复可执行，无“待补”的核心 destructive 阶段。
4. Windows/macOS 干净机器安装，独立应用数据/keyring 不覆盖旧产品，Linux Docker 主机可操作。
5. 版本/签名/发行身份在建项目时确定并验证；macOS/Windows 客户端架构与 Linux amd64 远端支持分开列出。
6. 交付恢复 runbook、受支持环境、已知限制、测试证据与发布包。若发布候选承诺 P1，则相应 P1 工作包也必须通过。
