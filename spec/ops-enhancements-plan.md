- 版本：1.0.5（规划）
- 日期：2026-11-02
- 状态：设计规划；未注册任何新 command，未改变现有行为
- 适用范围：Windows/macOS 桌面端，Linux amd64 + Docker Compose 远端
- 关联文档：[DST 更新](dst-update-plan.md)、[定时备份](scheduled-backup-plan.md)、[玩家列表与踢出](player-list-plan.md)

## 2. 当前基线

已实现并且应复用的能力：

- target 身份：所有实例业务携带 `serverId/hostId/instanceId`，不能以当前选中对象寻址。
- 任务：远端持久任务目录、controller、`systemd-run`、heavy/instance 锁、journal、阶段、operationId 幂等、断线对账。
- 备份：`backupCreate` 已支持 `cold` 和 `quasiHot`，有 metadata、checksum、verification、restorability、MOD 引用和恢复流程。
- Release：catalog、staging 产物、镜像 digest 固定、基础验证、实例 `active-release.json` 与确定性 Compose。
- MOD：主机内容库、实例 MOD Release、`modoverrides.lua`、`dedicated_server_mods_setup.lua`、应用任务和恢复时重建。
- 运行事实：容器标签、Compose 项目、进程、端口、版本、A2S 人数和诊断。

当前缺口：

- 没有 `get_update_status`、`check_instance_updates`、`preview_instance_update`、`run_instance_update` 的实现；`instanceUpdate` 只是契约中的枚举值。
- 没有备份策略、远端 scheduler、保留策略和定时来源标记；`quasiHot` 只能手动创建。
- 没有玩家名单来源。A2S 只能返回人数，不能返回名称/角色；DST 没有内建 RCON；日志解析不能可靠给出当前角色，也无法安全踢人。
- 备份恢复当前要求备份 Release 与活动 Release 相同；更新回滚需要“恢复旧存档并切回旧 Release”的受控路径。
- 删除 Release 只检查实例 manifest/active-release、任务和容器引用，未检查备份 metadata 的 Release 引用。

## 3. 共同约束

1. 不伪造成功。检查失败、结果未知、桥接未加载、回滚未验证都必须显示真实状态；不能返回“已更新”“已踢出”“已备份”。
2. 远端计时，不是桌面计时。桌面退出、SSH 断开后仍执行；应用重启后按持久状态对账。
3. 所有写操作绑定 target、revision/planId、operationId。计划过期、目标变化、Revision 变化都重新预览。
4. 锁顺序固定：registry → heavy → maintenance/instance → task。持有内存锁时不做 I/O；Rust 阻塞 I/O 进入 `spawn_blocking`。
5. 密码、Token、SSH 密钥不进入 SQLite、草稿、日志、事件、诊断。玩家名称和 Klei userid 属于运行数据，也不写入日志、任务事件、诊断包或备份归档。
6. 单一实现。准热备份、删除校验、Compose 渲染、MOD overrides 生成、恢复提交都复用现有函数，不为新功能复制第二套规则。
7. 只有已实现的能力才注册 command；未完成前页面不显示可点击的假入口。
8. UI 保持极简；不添加常驻流程说明。状态、时间、阻断原因和危险后果按条件显示。
9. 远端仅 Docker Compose；不引入 RCON 服务、不挂 Docker socket、不新增第二套部署模式。
10. 必须通过现有检查：`npm run check`、Rust fmt/check/test/clippy `-D warnings`、远端 Python fixture、亮暗主题和 960×680/1480×920。
11. 前端查询沿用现有 contextEpoch/requestSeq/revisionFloor 规则；成功、error 和 finally 都校验，旧响应不能写入新 target。

## 4. 功能之间的依赖

```text
                    ┌────────────────────────────┐
                    │ Release 构建 / 登记 / 验证 │
                    └─────────────┬──────────────┘
                                  │ 提供 verified release
                                  ▼
┌───────────────┐        ┌──────────────────┐        ┌──────────────────┐
│ 定时备份      │        │ DST 实例更新     │        │ 玩家列表与踢出   │
│ scheduler     │        │ update task      │        │ bridge mod       │
└───────┬───────┘        └────────┬─────────┘        └────────┬─────────┘
        │                         │                           │
        │ 复用 backupCreate       │ 依赖冷保护备份             │ 需要 Compose 挂载
        │ 复用 controller/锁      │ 依赖恢复/回滚路径           │ 需要 modoverrides
        │ 产生 scheduled origin   │ 更新后桥接需复验           │ 更新后桥接需兼容
        └───────────────┬─────────┴───────────────┬───────────┘
                        ▼                         ▼
              ┌────────────────────┐    ┌──────────────────────┐
              │ 备份 metadata/origin│    │ 实例 Compose/配置变更 │
              │ 保留与引用保护      │    │ 一次性重开分片        │
              └────────────────────┘    └──────────────────────┘
```

具体影响：

- **更新 ↔ 备份**：更新必须先创建冷保护备份；保护备份的 Release 引用必须被保留，否则无法回滚。更新后旧的同版本恢复限制会阻止把保护点恢复回去，需增加受控的版本切换回滚路径。
- **定时备份 ↔ 更新**：定时任务遇到实例更新、恢复、MOD 应用或手动备份时跳过（不排队）；不得在破坏性操作窗口插入准热备份。更新完成后下一次定时备份自然采集新版本。
- **玩家桥接 ↔ 更新**：桥接是本地服务端 MOD，更新只换 DST 镜像，不换桥接代码；更新验证阶段应确认桥接仍产生状态文件，失败只降级玩家功能，不把更新判失败。
- **玩家桥接 ↔ Compose/MOD**：需要给实例增加固定本地 MOD 目录挂载和 `modoverrides.lua` 固定项；新建实例默认带桥接，已有实例需要一次明确的重开分片迁移。
- **定时备份 ↔ Compose**：不需要改 Compose，只新增远端 systemd timer 和策略文件；删除实例时清理策略和计时状态。

## 5. 实施顺序

### M0：技术验证（3–5 人日，先做）

目标是在写正式页面之前消除两个外部不确定性：

1. 玩家桥接 MOD 能否在真实 Linux amd64 主机、真实 DST 客户端下加载；`io.open` 能否写桥接目录；`TheNet:DropPlayer` 或等价 API 能否踢人；Master/Caves 迁移时名单是否正确。
2. 用当前 runtime 镜像内的 SteamCMD 执行 `app_info_print 343050`，能否稳定取得数字 buildid；网络失败、镜像缺少 SteamCMD、输出格式变化时能否明确失败。

退出条件：真实主机上分别完成两份可重复的验证记录。任一失败，不进入对应功能的 UI 开发；只记录阻断原因和替代方案。

### M1：定时备份（14–20 人日）

为什么先做：依赖最少，复用现成 `backupCreate`，能立即降低运维风险；同时巩固更新所需的任务、锁和 metadata 基础。定时备份本身是准热备份，不是更新前的保护点。

交付：

- 远端全局 scheduler（systemd timer + oneshot），策略文件、调度状态、安装/校验。
- `get_backup_policy` / `save_backup_policy`，策略 revision CAS。
- 定时 `quasiHot` 备份，`origin=scheduled`，missed-run 去重和跳过原因。
- 保留策略（count/age/minFreeBytes），只清理 scheduled，至少保留一份 verified。
- 备份页策略区、下次/上次执行、最近错误；备份列表来源标签。
- 桌面关闭、主机重启、断网、磁盘不足、手动备份冲突的验收。

完成条件：桌面退出 24 小时后远端仍有新的 verified scheduled 备份；主机重启后只补一次错过的窗口；关闭策略后不再新增；任何删除失败都保留索引和可见错误。

### M2：DST 更新（21–32 人日）

为什么第二：依赖 Release 构建和回滚路径，风险最高；定时备份先落地后，更新前的保护点不需要另写一套。

交付：

- 主机级更新检查（SteamCMD app_info_print + 缓存 + 失败保留旧检查时间）。
- `get_update_status`、`check_instance_updates`、`preview_instance_update`、`run_instance_update`。
- `instanceUpdate` 持久任务：preflight → stagingVerify → stop → backup → publish → start → verify → finalize；失败进入 rollback。
- 活动 Release 切换、Compose 重渲染、实际 build 证据、其他实例不变性证据。
- 受控回滚：恢复保护点 + 切回旧 Release，旧产物/备份不全时禁自动回滚。
- Release 引用保护：备份引用、活动 Release、任务引用阻止删除。
- 更新页、Release 缺失时的构建入口、失败/已恢复原版本的真实文案。
- 三实例隔离、SSH 断开、主机重启、磁盘不足、回滚失败验收。

完成条件：更新 A 后 B/C 的 manifest、Compose、运行状态和文件摘要不变；更新失败且保护点完整时恢复旧版本并明确标记“更新失败，已恢复原版本”；旧产物缺失时预览明确标记不支持自动回滚。

### M3：玩家列表与踢出（17–27 人日，含技术验证）

为什么最后：依赖 M0 的桥接验证和 Compose/MOD 变更；如果先做页面，桥接不成立会产生大量返工。

交付：

- 本地桥接 MOD（`modinfo.lua` + `modmain.lua`），固定目录挂载，状态文件与命令/结果协议。
- 新建实例默认安装桥接；已有实例一次性启用任务（明确重开分片影响）。
- `get_instance_players`：Master/Caves 合并、去重、时间/新鲜度、桥接健康状态。
- `kick_instance_player`：确认、命令文件、结果等待、超时未知、刷新。
- 玩家页：名称、角色、分片、踢出；角色映射和未知 prefab 回退；空/未启用/过期/失败状态。
- 真实客户端验收：Master、Caves、角色切换、改名/Unicode、踢出、离线、迁移中、桥接未加载。
- 更新后桥接兼容复验。

完成条件：在线玩家列表与真实客户端一致；踢出只对在线目标返回成功；结果未知不会显示成功；玩家名称和 userid 不进入日志、任务事件、备份或诊断。

| 场景 | 定时备份 | DST 更新 | 玩家列表 |
| --- | --- | --- | --- |
| 桌面关闭 | 仍执行 | 任务继续（远端 controller） | 页面不可用，不承诺实时 |

## 9. 跨功能设计决定

| 决定 | 结论 | 原因 |
| --- | --- | --- |
| 定时器位置 | 远端 systemd timer + oneshot，不用桌面计时器 | 桌面关闭仍执行；控制器本来就用 systemd；不挂 Docker socket |
| 定时备份模式 | 固定 `quasiHot`，允许实例停止时采集 | 用户明确要求准热备份；不因定时任务停服；准热不作为破坏性操作保护点 |
| 定时备份来源 | `origin=scheduled`，只对 scheduled 自动保留 | 不误删手动备份和保护点 |
| 更新前保护点 | 强制冷备份 | 回滚必须包含存档+旧二进制+MOD+配置 |
| 更新执行范围 | 单实例，不做批量 | 隔离和失败影响可控；共享 Release 不共享实例状态 |
| 旧版本恢复 | 更新任务走受控回滚；普通恢复暂不默认允许跨版本 | 避免用户在普通恢复中误切版本 |
| 玩家数据来源 | 自带服务端桥接 MOD，不依赖 Workshop | 不引入第三方版本/下架风险；可控协议 |
| 桥接安装 | 新建默认启用；已有实例显式启用并重开分片 | 不在用户不知情时改游戏运行配置 |
| 踢出语义 | 只踢出，不封禁、不加黑名单 | 用户只要求踢出；封禁涉及访问策略和备份边界 |
| 玩家数据持久化 | 只读远端快照，不写 SQLite/日志/事件/诊断 | 降低个人信息和过期数据风险 |

## 10. 未决问题

在进入对应里程碑前需要产品确认：

1. **优先级**：是否接受“定时备份 → 更新 → 玩家”的顺序，还是更新必须先做？如果是后者，M1 与 M2 对调，但 M0 仍应先做。
2. **更新是否自动构建 Release**：v1 建议更新页只提示“缺少 Release”，跳转 Release 管理构建；不在更新任务里顺手构建。若希望一键“构建并更新”，需要把构建任务和更新任务串成一个长任务，失败语义更复杂，工作量增加约 4–6 人日。
3. **玩家桥接默认值**：新建实例默认启用是否可接受？已有实例是否允许保持关闭（页面显示未启用）？
4. **定时计划粒度**：v1 建议只支持“每 N 分钟/小时”间隔，不支持“每天 HH:mm + 时区”；后者需要额外处理时区、夏令时和错过窗口。
5. **普通恢复是否允许跨版本**：v1 建议只在更新回滚中允许；如果希望在备份页手动恢复旧版本，应作为独立确认流程，不与普通恢复混用。
6. **玩家名称/ID 的保留时间**：v1 建议仅在远端内存/文件快照中存在，不写本地数据库；若以后要做玩家历史，需要单独的数据保留和隐私设计。

## 11. 本轮不做什么

- 不做 RCON、跳板机、任意远端命令输入或控制台透传。
- 不做批量更新、批量踢人、批量删备份。
- 不做自动更新（每次重启自动升级）或后台静默升级。
- 不做封禁/白名单/管理员编辑；玩家页只踢出。
- 不做玩家历史、在线时长排行、聊天记录。
- 不做跨主机自动迁移、备份上云、对象存储。
- 不在未通过真实主机验收前把功能标成“已支持”。

## 12. 完成定义

一个功能只有在以下全部满足时才从规划移入“已接入”：

1. 契约、Rust DTO、前端类型、调用点、fixture 和错误码同步。
2. 远端脚本有隔离 fixture，覆盖成功、失败、中断、重复 operationId、错误 target。
3. Rust 测试、前端 `npm run check`、fmt/check/test/clippy `-D warnings` 通过。
